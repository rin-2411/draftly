ABSTRACT
The digital media landscape has evolved into a high-velocity environment where journalists and content creators are constantly pressured to produce high-quality, accurately researched articles under tight deadlines. One of the most significant bottlenecks in this process is the "research-to-synthesis" phase, where a writer must locate, read, analyze, and synthesize information from multiple disparate web sources before drafting a narrative. While Generative Artificial Intelligence (GenAI) has made strides in text production, generic models often suffer from "hallucinations" or lack specific context regarding niche current events. This project proposes the development of a specialized AI Content Generator designed specifically for journalists and bloggers. Unlike standard chatbots, this system implements a Retrieval-Augmented Generation (RAG) approach where the user feeds specific URLs as the "ground truth." The system automates the extraction of text from these user-provided links, analyzes the semantic relationships between the different sources, and generates a coherent article draft based strictly on the fed material. By bridging web scraping technologies with Large Language Models (LLM), this application aims to significantly reduce the cognitive load and time required for preliminary drafting, allowing writers to focus on editorial tone and investigative nuance rather than manual compilation.

CHAPTER 1
INTRODUCTION
Project Background
The advent of the Information Age has fundamentally altered the landscape of journalism and digital content creation. We have moved from a scarcity of information to an overwhelming abundance. Today, a single news event or product release is covered by hundreds of disparate sources, each offering different facts, statistics, and perspectives. For professional journalists and bloggers, the core skill set has shifted from simply "finding" news to "synthesizing" it effectively for their audience [1].
Recent studies in digital media workflows indicate that a significant portion of a writer's time—estimated between 30% to 50%—is spent on the mechanical tasks of reading, cross-referencing, and organizing notes from various web pages before a single sentence of the final draft is written [2]. This high cognitive load contributes to a phenomenon known as "information fatigue," which can degrade the quality of the final output and lead to burnout among professionals.
Simultaneously, the field of Software Engineering and Artificial Intelligence (AI) has seen a paradigm shift with the introduction of the Transformer architecture in 2017 [3]. These models, which underpin modern Large Language Models (LLMs), have demonstrated unprecedented capabilities in Natural Language Understanding (NLU) and Natural Language Generation (NLG). While these technologies have been widely adopted for simple chatbots and creative writing assistants, their application in rigorous, multi-source journalistic workflows remains an under-explored area of implementation. This project seeks to bridge that gap by applying advanced Software Engineering principles to solve a critical workflow inefficiency in the media sector.
Problem Statements
Despite the proliferation of AI writing tools, the specific workflow of multi-source content aggregation remains inefficient and largely manual for professional writers.
Inefficiency of Manual Synthesis: Journalists and bloggers typically operate with multiple browser tabs open, manually toggling between sources to gather facts. This "context switching" breaks the writer's flow state and significantly slows down the production process [4].
Lack of Specialized Tools: Existing AI tools (such as ChatGPT or Jasper) generally operate on a "Prompt-to-Text" basis. They are excellent at creative writing from scratch but struggle when a user needs to write a factual report based on specific external articles. There is a lack of accessible tools that allow a user to simply feed multiple URLs and receive a synthesized draft in return.
Accuracy and Hallucination Risks: When writers rely on generic AI models without providing specific source material, the AI is prone to "hallucinations"—fabricating facts or statistics [5]. There is a critical need for a system that grounds its generation in specific, user-verified links to ensure the content remains factual.

Project Objectives
The primary aim of this project is to develop a functional web-based application that automates the creation of articles by synthesizing text from multiple user-provided URLs. To achieve the main aim, the following specific objectives have been defined:

To develop a robust Web Scraping Module: To implement algorithms capable of extracting clean, readable text from diverse HTML structures of news websites and blogs, while filtering out noise such as advertisements and navigation menus [6].

To implement Multi-Document Summarization Logic: To engineer a backend pipeline using Natural Language Processing (NLP) that aggregates extracted text, removes redundant information across sources, and generates a cohesive summary.

To design a User-Centric Interface for Writers: To create an intuitive front-end interface where non-technical users (journalists/bloggers) can easily manage their source links, customize the desired tone (e.g., professional, casual, opinionated), and view the generated output for editing.
To implement a Context-Aware Generation Engine: To integrate a Large Language Model (LLM) utilizing a Retrieval-Augmented Generation (RAG) architecture. This ensures the model processes the extracted text from the user's URLs and synthesizes it into a new article, adhering strictly to the context provided by the feeds.

To evaluate System Performance: To test the system using standard text similarity metrics (ROUGE) and conduct User Acceptance Testing (UAT) to measure the utility and quality of the generated content.


Project Scopes
The scope defines the boundaries of the project to ensure it is achievable within the final year timeframe.
Target Users: The system is designed specifically for online journalists, tech bloggers, and content marketers.
Input Data: The system will accept standard HTTP/HTTPS URLs. It is optimized for text-heavy pages (articles, blog posts, wikis).
Output Language: The system will support processing and generation in the English language only.
Platform: The solution will be delivered as a responsive Web Application (accessible via browser)..

Expected Outcome
The completion of this project is expected to deliver a robust solution for automated journalism and content creation. The outcomes are categorized into technical deliverables impact: 

The Draftly Web Application: A high-performance web platform built with Next.js and integrated with Supabase and OpenAI API.

Spider Crawl Module: A specialized web crawling component capable of navigating diverse HTML structures to extract high-quality, relevant text data while bypassing non-essential elements like advertisements and navigation sidebars.

Article Synthesis Engine: A refined prompt-engineering logic that transforms raw, unstructured data from multiple sources into a singular, cohesive article draft tailored to specific tones and lengths.

Related Studies
 	       2.2.1	The Evolution of Automated Journalism
The concept of "Automated Journalism," often referred to as "Robot Journalism," has evolved significantly over the past decade. Early implementations, as documented by [7], relied on rigid templates to fill in data for weather reports and sports scores. These systems were rule-based and lacked the ability to generate creative or nuanced text.

However, the field has recently shifted towards "Augmented Journalism." Research by [8] suggests that the goal of modern AI in newsrooms is not to replace human reporters but to augment their capabilities. The study highlights that while AI can process data faster than humans, it lacks the "editorial judgment" and "ethical reasoning" required for final publishing. This literature supports the design philosophy of this project: the system is intended to be a drafting assistant (Human-in-the-loop), not a fully autonomous publisher.
		     2.2.2   Multi-Document Summarization (MDS) Techniques
The core technical challenge of this project lies in Multi-Document Summarization (MDS).
Extractive Summarization: Traditional approaches utilized extractive methods, which algorithmically selected and rearranged the "most important" sentences from the original texts [9]. While computationally efficient, studies show that this method often results in disjointed flow and poor readability.
Abstractive Summarization: With the rise of Deep Learning, the focus has shifted to abstractive summarization. As detailed in [10], models like BERT (Bidirectional Encoder Representations from Transformers) and GPT (Generative Pre-trained Transformer) can understand the semantic meaning of the text and generate new sentences that capture the essence of the source material. This project will utilize abstractive techniques to ensure the generated blog posts sound natural and human-written.
A key challenge in MDS identified by [11] is "Redundancy." When summarizing three news articles about the same event, the AI must be smart enough to recognize that all three mention the same core fact and merge them, rather than repeating the fact three times.
2.3   Existing Systems Review
To establish the viability of the proposed project, a critical analysis of current market-leading AI content generators was conducted. While numerous tools exist, most are designed for marketing copy (persuasion) rather than journalism (factual synthesis). This section details the features, strengths, and limitations of three prominent systems: Jasper AI, Copy.ai, and Frase.io.
		          2.3.1  Jasper AI
Jasper AI is widely considered the market leader in generative AI for enterprise marketing. It utilizes a combination of open-source models (like GPT-4) and proprietary marketing data to generate high-converting copy.
Core Features: Jasper operates on a "Template" and "Chat" system. Users select a template and input a short text description or keywords. It recently introduced "Brand Voice" to mimic a company's style.
Strengths: It produces highly creative and grammatically superior text. Its integration with SurferSEO allows marketers to optimize content for Google rankings [12].
Weaknesses (The Research Gap): Jasper is designed to create ideas, not report on them. It lacks a native workflow for "Multi-Source Synthesis." If a journalist wants to write an article based on three specific news reports, they must manually paste snippets into Jasper's chat window one by one. Furthermore, as a creative tool, it has a high tendency to "hallucinate" (fabricate) quotes and statistics when not strictly grounded in provided text, making it risky for factual news reporting [13].

 		  2.3.2 Copy.ai
Copy.ai targets social media managers and freelance copywriters who need rapid, short-form content.
Core Features: It offers a "Chat" interface similar to ChatGPT but with pre-built prompts for social media captions, email subject lines, and ad copy.
Strengths: It is extremely user-friendly with a low learning curve. It offers a free tier that makes it accessible to students and hobbyists [14].
Weaknesses: The system struggles significantly with Long-Form Coherence. While it can write a great Instagram caption, it often loses context when attempting to write a 1,000-word article, resulting in repetitive phrases. Crucially for this project, it does not support a "URL-to-Article" feature where the AI reads a link and writes a report; it relies entirely on the user typing the context manually [15].

 	      2.3.3 Frase.io
Frase is the closest technical competitor to the proposed system. It is an SEO-focused tool that helps content strategists research keywords.
Core Features: Frase can scan the "Top 20 Google Results" for a keyword and extract the headings (H1, H2) to help a user build an outline.
Strengths: It excels at structural research, helping users understand what topics their competitors are covering.
Weaknesses: Frase is an SEO tool, not a Writing tool. While it can generate text, its primary goal is "Keyword Stuffing" (ranking high on Google) rather than "Narrative Flow" (readability). It often produces robotic text designed to please search engine algorithms rather than human readers. Additionally, it is expensive (starting at $45/month), placing it out of reach for independent journalists [16].

Research Gap and Analysis
Despite the rapid advancement of Large Language Models (LLMs) and the availability of commercial writing tools, a critical review of the literature reveals significant gaps when applying these technologies to professional journalistic workflows.


2.4.1       The "Hallucination-Grounding" Gap

A primary limitation of current Generative AI models is the phenomenon of "hallucination," where models fabricate facts to satisfy a prompt. Research by Ji et al. (2023) indicates that LLMs prioritize linguistic fluency over factual accuracy when generating text from open-ended prompts [17]. Existing tools like Jasper AI operate on this "open-ended" basis, making them unsuitable for news reporting where factual integrity is paramount. There is a distinct lack of tools that enforce "Source-Grounding"—restricting the AI to generate content only from user-provided URLs.

2.4.2       The "Multi-Source Synthesis" Workflow Gap

While Multi-Document Summarization (MDS) is a well-researched field in academia, practical implementations for non-technical users are scarce. El-Kassas et al. (2021) highlight that most MDS systems are experimental command-line tools that require technical expertise to run [18]. Conversely, commercial tools like Copy.ai focus on single-document processing or creative fiction. There is a "usability gap" for a web-based interface that allows a journalist to input three distinct news sources (e.g., three different URLs reporting on an event) and receive a single, non-redundant synthesized draft.

CHAPTER 4

SYSTEM DESIGN

  System Design
The purpose of this chapter is to detail the technical specifications and structural blueprint of the AI Content Generator. This process translates the functional and non-functional requirements (Chapter 3) into a concrete, implementable design. The system design is divided into three key areas: the system architecture, which defines the relationships between components; the interface design, which details the user interaction; and the database design, which outlines data storage and retrieval.

 System architecture
The system employs a Three-Tier Client-Server Architecture augmented by an external Large Language Model (LLM) service. This design choice is optimal for a web-based AI application as it ensures the security of the proprietary AI key and offloads heavy computational tasks to a dedicated external service (OpenAI), thereby achieving high performance (NFR-01). The system is built using the Next.js framework, which unifies the Presentation and Application layers.The three parts are:
The system is organized into the following layers:
Presentation Layer (Frontend): The user-facing component built with Next.js (React). It manages the UI, user input (URLs, tone selection), and displays the final editable draft.
Application Layer (Backend Logic): Handled by Next.js API Routes. This layer contains the core business logic, including the Web Scraper Module and the OpenAI Controller. This separation is crucial for securing the API key.
Data Layer (Storage/External Services): This includes the target websites from which data is scraped and the OpenAI API, which acts as the core processing engine.
The figure below shows how these three parts and the three user roles connect.


Figure 4.2 Component Relationship
Discussion on Component Relationship:

User Interaction (Client): The user submits URLs via the React frontend. This request is sent to a specific Next.js API Route (e.g., /api/generate).
Web Scraping Module: The backend API Route first invokes the web scraping module. This module executes an external HTTP request to the target URLs to fetch raw HTML. This task is placed on the server-side to bypass browser security restrictions.
Data Cleaning: The raw HTML is passed through a sanitizer to extract only clean, semantic text, removing all noise.
AI Controller: The cleaned text is compiled into a single, cohesive System Prompt, which includes instructions on tone (from FR-04) and a directive to avoid hallucination.
External LLM Processing: The prompt is sent to the OpenAI API. OpenAI performs the complex task of multi-document abstractive summarization.
Response and Output: The generated text is received by the backend, then passed back to the frontend where it is displayed in the Rich Text Editor (FR-06).

5.3 System Implementation Overview

The implemented system is organised into three logical layers consistent with Chapter 4:

1. Presentation layer — React pages and client components under `src/app` and `src/components`.
2. Application layer — Next.js API routes under `src/app/api` and business logic under `src/lib`.
3. Data layer — Supabase PostgreSQL tables with Row Level Security (RLS).

Route structure (journalist workspace): After authentication, users access a shared workspace layout at top-level routes: `/` (home hub), `/drafts` (Overview editor), `/saved-drafts`, `/research`, `/templates`, and `/settings`. Legacy `/dashboard/*` URLs redirect to these paths via middleware.

Route structure (administration): Administrators access `/admin` and sub-routes (`/admin/users`, `/admin/drafts`, `/admin/logs`, `/admin/settings`), protected by middleware and server-side role checks.

5.4 Core Module Implementation

5.4.1 User authentication module

Authentication is implemented with Supabase Auth. Pages under `src/app/auth/` provide login, signup, forgot-password, and reset-password flows. The `src/middleware.ts` file refreshes the session on each request and enforces access control:

- Unauthenticated users are redirected to `/auth/login` when accessing protected workspace routes.
- Authenticated users are redirected away from login/signup to the home hub.
- Disabled users (flag in `profiles.is_disabled`) are blocked from the workspace.

Sign-out is handled via `POST /api/auth/signout`. Passwords are hashed by Supabase; the application never stores plain-text credentials (NFR-05).

5.4.2 Content generation module (source-grounded synthesis)

This module fulfils the core functional requirements FR-01 (URL input), FR-02 (scraping), and FR-03 (AI synthesis).

Client flow: On the Overview page (`DashboardClient.tsx`), the user enters up to five URLs in the Research sources panel, selects tone, length, and output language, and triggers generation via Research full draft, Generate outline, or Check facts. The client sends `POST /api/generate` with `{ urls, tone, length, language }`.

Server flow (`/api/generate/route.ts`):

1. Verify user session; reject disabled accounts and maintenance mode.
2. Enforce daily generation limit from `system_settings`.
3. Validate input with `generateRequestSchema` (Zod).
4. Call `crawlUrls()` in `src/lib/crawl/index.ts`, which posts each URL to Spider.cloud and returns markdown text or per-URL errors (10-second timeout per URL).
5. Call `synthesizeContent()` in `src/lib/llm/index.ts`, which builds a system prompt requiring facts-only output, specified tone, length band, and output language, then invokes GPT-4o.
6. Persist a new row in `drafts` via `createDraft()`.
7. Log the attempt in `generation_logs` (success or failure, crawl counts).
8. Return draft JSON and crawl status to the client.

The editor is updated with the generated title and body. An Undo control restores the pre-generation editor state from a client-side stack (up to 25 steps).

Note on assistant buttons: All three AI buttons use the same generation endpoint; they differ in preset tone/length before the request. This is documented as a design simplification for the prototype.

5.4.3 Draft management module

Drafts are stored in the `drafts` table. API routes:

- `GET/POST /api/drafts` — list and create drafts.
- `GET/PUT/DELETE /api/drafts/[id]` — read, update, delete by id.

Server functions in `src/lib/drafts/index.ts` always scope queries with `user_id = auth.uid()` so RLS and application logic align. The Overview editor performs debounced auto-save (~1.3 s after typing) when a draft id exists, and manual save via button or Ctrl+S. Saved drafts are listed on `/saved-drafts` and can be reopened with `/drafts?draftId=<uuid>`.

5.4.4 Research library module

The Research Library (`/research`, `ResearchLibraryClient.tsx`) allows users to save sources with URL, optional title, notes, and tags. CRUD operations use `/api/research-library` and `/api/research-library/[id]`. Users can select sources and open them in Overview with pre-filled URLs (`/drafts?prefillUrls=...`), supporting the research-to-draft workflow identified in Chapter 2.

5.4.5 Templates module

Built-in story templates are defined in `src/lib/templates/builtins.ts` (wire brief, news feature, opinion column, Q&A, investigative, newsletter, etc.). The Templates page links to `/drafts?template=<id>`, which pre-fills title, section outline with placeholders, tone, and length. Templates are intended primarily for manual structured writing; AI generation uses tone/length defaults but does not yet inject the outline into the LLM prompt (see Section 7.3).

5.4.6 User preferences module

The Settings page (`/settings`, `SettingsClient.tsx`) updates display name, default tone, length, and output language via `PATCH /api/user/preferences`, stored in Supabase `user_metadata`. Users can export all drafts as JSON from the client. These defaults apply when opening a blank Overview session.

5.4.7 Administration module

Administrative features were added to support monitoring and governance:

 Feature | Implementation |
---------|----------------|
 Role detection | `ADMIN_EMAILS` env or `user_metadata.role = admin` |
 User management | List auth users, promote/demote admin, disable accounts |
 Draft moderation | Search and delete any user's draft (service role) |
 AI audit logs | `generation_logs` table populated on each generate call |
 System settings | Maintenance mode, announcement banner, daily generate cap |

Admin APIs live under `/api/admin/*` and use `createAdminClient()` with the service role key. The admin UI is implemented in `src/components/admin/`.

5.4.8 Output language enhancement

Beyond the original SRS (English-only), the implementation supports sixteen output language options including Auto (match sources), English, Bahasa Malaysia, Chinese, Tamil, and others. The selected language is passed to the LLM system prompt via `src/lib/output-languages.ts`.

5.5 Database and Security Implementation

Three SQL migrations define the schema:

1. 001_create_drafts_table.sql — `drafts` table, indexes, RLS policies, `updated_at` trigger.
2. 002_research_sources.sql — `research_sources` table with RLS.
3. 003_admin.sql — `profiles`, `generation_logs`, `system_settings`, trigger on new auth users.

Security measures implemented:

- RLS on all user tables (select/insert/update/delete own rows only).
- API keys for OpenAI and Spider only on server routes.
- Middleware session refresh and route protection.
- Admin operations isolated to service-role server client.
- Input validation with Zod on all mutating API endpoints.

7.3 Limitations

The following limitations were identified during implementation and testing:

1. Crawl dependency: Generation quality depends on Spider.cloud successfully extracting text. Paywalled, JavaScript-heavy, or social-media URLs often fail.
2. Template–AI gap: Selecting a template pre-fills the editor but does not instruct the AI to follow section headings; generation replaces the outline unless the user uses Undo or manual editing.
3. Assistant button semantics: Research full draft, Generate outline, and Check facts share one generation pipeline with different length presets rather than distinct outline or fact-check algorithms.
4. Scale: User listing and statistics use admin APIs suitable for small-to-medium user bases; large-scale deployment would require pagination and background jobs.
5. SRS deviation: Multi-language output was added beyond the original English-only scope (Version 1.0 SRS); this is an enhancement but should be noted for documentation consistency.

7.4 Future Work

Recommended extensions for future versions:

- Pass template structure into the generation prompt for template-faithful AI drafts.
- Dedicated outline-only and claim-vs-source verification modes.
- Improved extractors for difficult URLs (Readability APIs, publisher partnerships).
- Collaborative newsroom features (shared research folders, editor roles).
- Automated test suite (Jest/Playwright) and performance metrics dashboard.
- Publishing integrations (WordPress, CMS export formats).

7.5 Conclusion

The digital journalism industry continues to face information overload while audiences expect rapid, accurate reporting. This project has demonstrated that a source-grounded AI writing workspace can be engineered with modern web and AI tools to support—not replace—the journalist. By anchoring generation to user-supplied URLs, Draftly prioritises factual grounding over unrestricted text generation and aligns with responsible use of Large Language Models.

The journey from requirements (Chapter 3) and design (Chapter 4) to implementation (Chapter 5) and validation (Chapter 6) confirms that the proposed architecture is viable. The prototype is ready for demonstration, supervisor review, and further refinement in professional or academic settings.

The project fulfils its goal of bridging web scraping, LLM synthesis, and secure cloud persistence into a single cohesive tool for journalists and bloggers, and establishes a foundation for continued development beyond the Final Year Project timeframe.

The software product to be produced is named the AI-Powered Content Generator. It is a specialized web-based application designed to facilitate the rapid synthesis of journalistic content from multiple external sources.

Project Scope :

In Scope (What the system will do):

Multi-Source Ingestion: The system will accept multiple user-provided URLs (up to 5 unique links) as the primary input for content generation.

Paywall Penetration: The system will not attempt to bypass authentication walls, strict paywalls, or complex CAPTCHA challenges on target websites.

Multi-Language Support: The system will not support translation or generation in languages other than English in this release (Version 1.0).

Primary Objective of the project: To automate the cognitive-heavy tasks of reading, summarizing, and synthesizing multiple documents, thereby reducing the time required to move from research to a working draft.

Key benefits of the project : 

Efficiency: Reduces the "Research-to-Draft" cycle time by approximately 50%, allowing writers to focus on high-level editorial tasks.

Accuracy (Reduced Hallucination): Unlike generic AI writing tools that generate content from open-ended prompts, this application grounds its output in specific, user-verified URLs, significantly increasing factual reliability.

Workflow Streamlining: Consolidates the fragmented process of opening multiple tabs and manually copy-pasting notes into a single, unified dashboard interface.

2.1.1 System interfaces 
The AI-Powered Content Generator relies on interactions with several external systems and environments to function. This subsection lists these critical interfaces, the functionality they support, and the technical description of the interface.
1. Web Browser (Client Interface)
Functionality: The Web Browser acts as the primary host for the frontend application. It renders the User Interface (UI), captures user inputs (URLs, tone settings), and displays the final generated content. It is responsible for executing the client-side JavaScript (Next.js/React) logic.
Interface Description: The system is designed to run on any modern, standards-compliant web browser (e.g., Chrome v90+, Firefox v88+, Safari v14+, Edge). Communication between the browser and the application server occurs via HTTPS (Hypertext Transfer Protocol Secure) over standard port 443. The interface renders standard HTML5, CSS3, and ECMAScript 6+ (JavaScript).
2. OpenAI API (AI Processing Interface)

Functionality: This interface provides the core intelligence of the system. The application sends cleaned text data and prompt instructions to this system and receives the synthesized, abstractive summary in return.
Interface Description: The system communicates with the OpenAI backend via a RESTful API. Data is exchanged using JSON (JavaScript Object Notation) payloads. Authentication is handled via a secure Bearer Token (API Key) stored on the server side. The specific endpoint used is the Chat Completions API (POST https://api.openai.com/v1/chat/completions).
3. Supabase Platform (Database & Auth Interface)
Functionality: This interface handles two critical functions: managing User Authentication (signup, login, session tokens) and providing persistent storage for User History (saving generated drafts).
Interface Description: The application interfaces with Supabase using the supabase-js client library, which acts as a wrapper for Supabase's REST and Realtime APIs. It connects to a hosted PostgreSQL database. Secure connections are maintained using API keys (public anon key for client-side, private service_role key for server-side operations) and JWT (JSON Web Tokens) for user sessions.
4. Target Websites (Data Source Interface)
Functionality: The system must interface with arbitrary third-party websites provided by the user to "read" their content. The Web Scraper module retrieves the raw HTML structure of these pages to extract the body text.
Interface Description: The system creates outbound HTTP/1.1 GET requests to the user-specified URLs. It receives standard HTML documents in response. The system parses the Document Object Model (DOM) of these external pages to filter and sanitize text content.

2.1.6 Memory constraints  
This subsection specifies the limitations and characteristics regarding primary (RAM) and secondary (Storage) memory usage for both the client (user's device) and the server.
1. Primary Memory (RAM) - Server Side
Execution Limit: The system backend operates in a serverless environment (Next.js/Vercel). Each API Route execution (specifically the crawler and generation functions) is limited to 1024 MB (1 GB) of RAM.
Processing Constraint: The Spider Crawl engine and text processing modules must optimize memory usage to stay within this limit. Attempting to process extremely large documents (e.g., loading a 10MB text file into memory) simultaneously may trigger an Out of Memory (OOM) error. The system implements a "chunking" strategy to process large texts in smaller segments.
2. Primary Memory (RAM) - Client Side
Browser Heap: The frontend is a Single Page Application (SPA). It is designed to operate efficiently within a standard browser memory footprint (typically < 200 MB per tab).
UI Performance: The Rich Text Editor component is constrained to handle active drafts up to 20,000 words without causing significant "input lag" or browser freezing due to excessive DOM (Document Object Model) size.
3. Secondary Memory (Storage) - Database
Database Capacity: The Supabase (PostgreSQL) instance is provisioned with an initial storage capacity of 500 MB (Project Tier Limit).
Constraint: To adhere to this limit, the system does not store binary media (images, videos) directly in the database. Only text data (articles, logs) and metadata are persisted.
4. Local Storage (Client Cache)
Browser Storage: The application utilizes the browser's localStorage API for caching non-critical user preferences (e.g., last selected Tone). This storage is strictly limited by the web browser to approximately 5 MB per domain. The system is programmed not to cache full article histories here to avoid hitting this quota. 
2.1.7 Operations  
This subsection specifies the operational modes and procedures required for the normal functioning of the system, including user interactions, automated processing, and data safety measures.
1. Modes of Operation
Interactive Mode (Primary): The system is designed primarily for User-Initiated Operations. All core functions—Scraping, Generation, and Editing—are triggered explicitly by user actions via the web interface. There are no "always-on" background services that run without a user request.
Processing Mode (Wait State): Upon initiating a "Generate Content" request, the system enters a temporary processing mode. During this 30-60 second window, the user interface locks the "Generate" button to prevent duplicate requests while the Spider Crawler and AI Engine execute the task.

 Periods of Operations
Interactive Operations: The system supports 24/7 availability. Users can log in and interact with the dashboard at any time, provided they have an internet connection.
Unattended Operations:
Crawler Execution: Once the user submits URLs, the Spider Crawl engine operates unattended on the server to navigate and fetch data.
Token Management: The system automatically manages API session tokens (refreshing Supabase auth tokens) in the background without user intervention.

Data Processing Support Functions
Input Sanitization: The system automatically runs validation operations on all user inputs. URLs are checked for validity (HTTP/HTTPS format) before the crawler is engaged.
Content Filtering: Before sending data to the AI, the system performs an automated "cleaning" operation to strip HTML tags, scripts, and advertisements, ensuring only relevant text is processed.

4. Backup and Recovery Operations
Database Backups: The system relies on the managed backup operations provided by Supabase (Cloud Provider). Full database snapshots are taken automatically every 24 hours (Point-in-Time Recovery).
Data Recovery: In the event of a catastrophic server failure, the system operations team can restore the database to the state of the last valid snapshot.
Session Recovery: If a user accidentally closes the browser tab after generation but before saving, the system attempts to recover the text from the Local Storage cache upon the next login (if cached).

2.4 Constraints
This subsection describes the specific constraints and limitations that will affect the design and development of the AI-Powered Content Generator.

Regulatory and Policy Constraints

Data Privacy (GDPR/PDPA): The system stores user email addresses. Development must strictly adhere to data protection regulations. Passwords must never be stored in plain text; they must be hashed using industry-standard algorithms (managed via Supabase Auth).
OpenAI Usage Policy: The system must not generate content that violates OpenAI’s usage policies (e.g., hate speech, violence, illegal acts). The developer must implement a moderation check or error handling if the API refuses a request due to policy violations.
Copyright Compliance: The web crawler must respect the robots.txt file of target websites. The system is constrained to only scrape publicly available data and must not attempt to bypass login walls or scrape copyrighted content behind paywalls.

2. Hardware and Execution Limitations

Serverless Function Timeouts: The backend is hosted on a serverless platform (Vercel). The content generation process (Scraping + AI Synthesis) must complete within the 60-second execution timeout limit typically imposed by such platforms. This constrains the complexity of the scraping logic; if a process takes too long, it will be terminated.
Memory Limits: The Spider Crawler must operate within a 1024 MB RAM limit. It cannot load massive HTML DOM trees into memory simultaneously.

3. Interface and Connectivity Constraints

API Rate Limiting: The system is constrained by the rate limits imposed by the OpenAI API (Tokens per Minute). The developer must implement "Exponential Backoff" error handling to manage 429 Too Many Requests errors gracefully.
Dependency Reliability: The system is entirely dependent on the uptime of the OpenAI API and Supabase. If these services experience an outage, the application's core features will cease to function. The software cannot "failover" to a local AI model due to hardware limitations.

4. Higher-Order Language Requirements

Technology Stack: To ensure maintainability and compatibility with the student's skill set, the system must be developed using Next.js (React framework) for the frontend and Node.js for the backend logic.
Language: The source code should be written in TypeScript or JavaScript (ES6+) to ensure type safety and modern syntax standards.

5. Safety and Security Considerations

Secret Key Management: The OpenAI API Key is a critical secret. It is a strict constraint that this key must never be exposed to the client-side browser code. It must effectively remain in server-side environment variables.
Input Sanitization (XSS): The system scrapes untrusted HTML from external websites. Before this content is displayed to the user or sent to the AI, it must be rigorously sanitized to prevent Cross-Site Scripting (XSS) attacks.

6. Criticality of the Application

Non-Critical System: This is a productivity tool, not a safety-critical system. Failures in generation (e.g., a failed crawl) are acceptable provided they are communicated clearly to the user and do not result in data loss of previously saved drafts.

4.4.5 Portability 
ATTR-10 (Environment Independence): The application shall run on any system capable of running Node.js v18+. It should not rely on OS-specific binaries (e.g., Windows .exe or Linux-only packages) unless handled via Docker containers.
ATTR-11 (Browser Support): The frontend shall function identically on Chrome, Firefox, Safari, and Edge (current stable versions).
